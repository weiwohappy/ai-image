# 微信支付与支付宝：接入和启用

## 当前交付与边界

已实现微信 Native、支付宝电脑网站支付的下单、查单、回调验签和一次性积分包到账。没有商户信息时默认关闭，不会调用真实渠道。**代码实现不等于已经开通收款；尚未进行真实商户联调。**

付款页为 `/#/pricing`。原创作页仍是 Mock；新付款页不调用旧 `/mock/orders/:id/complete`，不修改演示余额。它使用后端真实账户、真实钱包和独立 API。当前支持登录后端已注册账户；开发账户可按主 README 使用 `seed:dev` 建立，原演示注册不等于真实注册。

首版是一次性、固定有效期积分包，不含自动扣费、分期逐月发放、并发升级或会员续费。现金退款、退款权益回收、渠道账单导入、已关闭订单的自动清理与运营后台不在本次交付内；生产启用前需明确并落实退款/争议运营流程。

## 本地运行

使用 Node 22，保留主 README 中的 PostgreSQL、Redis、邮件和存储配置，三个支付开关保持 false。

```sh
npm run prisma:migrate
npm run dev
```

前端 `viviai-web` 的 Vite 已将 `/api/billing` 代理至 `http://127.0.0.1:3001`；重新运行前端开发服务器后，付款页读取实际后端开通状态。没有后端时显示服务尚未连接，不伪造成功。生产环境需由同源反向代理把 `/api/billing/*`、`/api/webhooks/payments/*` 转发到 Nest API，不能只部署前端静态产物。

恢复扫描可单次运行，或每 30 秒持续运行：

```sh
npx tsx src/modules/billing/reconcile.ts
npx tsx src/modules/billing/reconcile.ts --watch
```

它只查持久化的未完成订单，不启动图片 Worker；无订单时无渠道请求。启用后必须常驻运行或通过运维调度执行。一个扫描最多 100 个订单，每订单数据库租约 30 秒，多实例不会在同一租约内同时查询。历史未结订单保留并持续查询；大规模上线需增加已关闭状态、退避、账单批量对账与运营分流，不能长期依赖这一基础扫描器。

## 商品与金额

`BILLING_CATALOG_FILE` 指向服务端私有 JSON 文件；格式参照 `billing-catalog.example.json`，**样例价格只是结构演示，不是已批准售价**。人民币以整数分计价，积分是整数，有效期 1–366 天。上线前根据真实模型成本确认售价并替换样例。

商品 id 是不可变版本号；修改价格、积分、有效期必须新建 id，不能复用旧 id 修改内容。订单内保存商品快照，后续配置调整不改变旧订单。每用户最多五个未到期未完成订单。

付费积分批次关联 PaymentOrder，流水类型 `paid_grant`，赠送依然是 `promotional_grant`。本增量中 `CreditLot.revenueMinor` 保存**已确认支付订单的总额**；未扣渠道费用，未考虑结算差异、补贴或现金退款，**不能把它当结算实收、净收入或利润**。这些需后续账单对账修正经营分析。

## 开通后需配置的资料

只在服务器环境/密钥管理服务中设置参数。私钥文件不得放前端、Git 或聊天。示例变量在 `.env.example`。

- 微信：Native 权限、绑定的 AppID、商户号、商户 API 证书序列号及私钥、API v3 密钥、微信支付公钥 ID/公钥、HTTPS 回调 URL。本版使用微信支付公钥模式，不是平台证书自动下载模式。
- 支付宝：电脑网站支付权限、AppID、卖家 ID、应用 PKCS8 RSA 私钥、支付宝公钥、HTTPS 回调/返回 URL。本版普通公钥模式，不是应用公钥证书模式。
- 至少一渠道正确配置、非空正式商品目录，再开启 `BILLING_ENABLED=true`。渠道开关可以独立启用。关闭新销售但需要继续接收历史回调时，仅关闭 BILLING_ENABLED，保留渠道配置和密钥。
- 当前环境只加载一个微信支付公钥 ID；轮换需保留在途请求使用的验证键并扩展配置，不能在处理未结订单时直接删旧键。
- HTTP 回调路径必须分别为 `/api/webhooks/payments/wechat` 和 `/api/webhooks/payments/alipay`。它们只靠验签，不使用浏览器 cookie；其他 POST 仍需合法 Origin。
- 支付宝返回页面仅为导航，不代表支付成功。用户可回到原付款页查询最近订单；支付宝打开在新标签页。

## 订单协议

| 接口                                     | 规则                                                                   |
| ---------------------------------------- | ---------------------------------------------------------------------- |
| GET `/api/billing/catalog`               | 公开开通状态、可售商品；不返回密钥和商户标识                           |
| GET `/api/billing/me`                    | 真实会话和钱包余额                                                     |
| POST `/api/billing/auth/login`、`logout` | 复用现有 IdentityService 与安全 cookie，不接收 Mock 身份               |
| POST `/api/billing/orders`               | `{planId,channel}`，必须带 16–100 位 Idempotency-Key，不接受客户端金额 |
| GET `/api/billing/orders/:id`            | 归属鉴权、只读数据库，不以刷新页面直接打上游                           |
| POST `/api/billing/orders/:id/sync`      | 归属鉴权、租约限频查询上游，回到统一履约入口                           |

订单状态：creating（创建结果未知）、pending、paid。对外展示 expired 只是支付入口过期，不声称上游绝无扣款。创建失败或超时保留原订单号，不自动重新创建；前端持久化幂等键及订单 ID，丢响应后重试原订单。合法迟到付款仍会到账，积分有效期从履约时开始。

到账事务统一核对订单、渠道、AppID、商户、金额、币种与交易唯一性，按钱包锁串行。通知事件、积分批次、流水、paid 状态原子提交；任何失败全部回滚。微信成功返回 HTTP 204 空体，支付宝返回纯文本 success；数据库未成功前不确认收妥。

## 正式启用前检查

1. 完成商户签约、经营类目/域名审核和真实模型交付能力；确认正式价格与用户权益说明。
2. 配置独立安全凭据、HTTPS 同源路由、日志脱敏、监控、备份与恢复扫描。
3. 使用各渠道允许的联调方式验证真实下单、响应签名、查单、通知、重复通知和网络中断；真实付款/退款须由商户明确批准后执行。
4. 补齐现金退款与权益撤销方案，验证已消费/冻结积分不会被粗暴扣成负数。
5. 修复基础依赖安全审计中剩余问题，完成生产环境安全审查。当前不得仅凭本地测试宣称生产可用。
