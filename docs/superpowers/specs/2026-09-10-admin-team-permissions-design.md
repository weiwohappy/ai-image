# 运营平台 B1：超级管理员、团队成员与角色管理

日期：2026-09-10。状态：用户已确认本详细设计，进入实施；功能是否完成以实施计划及验收记录为准。

## 1. 目标与交付边界

让内部团队直接在运营平台完成成员新增、资料编辑、角色分配、启用/禁用和密码重置；提供真正的 `super_admin`，不再以“业务负责人＋系统管理员”代替超级管理员。

本批包含真实页面、管理 API、数据库持久化、服务端权限校验、审计及测试。新增按钮不能以 Mock 成功代替数据库提交。沿用当前白底蓝色运营台，不重新设计整站视觉。

后续范围仍保留，未因拆分而取消：

1. B2：模型/官方规格、提供方账号与凭据、积分商品的新增、编辑及发布。
2. B3：用户资料与限制、积分补偿、订单同步/备注/退款申请、任务处置及告警处理。

本批不实现上述业务写操作，不开放生产环境，不调用模型、支付或邮件服务。审计记录永远不可编辑或删除。

### 与原总体设计的关系

原设计 `2026-09-09-operations-platform-design.md` 要求权限提升双人审批。为满足当前本地内部试用，本设计提议：**B1 团队管理在仅本机 development 环境中，由具备权限的管理员直接确认执行并留痕，不引入审批中心，不追加 MFA 步骤。** 这是待用户审阅确认的明确调整，而不是默认取消全部安全措施。

新增团队写接口必须满足 `NODE_ENV=development`、服务绑定回环地址、管理 Origin 全部为回环地址、请求来自实际回环地址；不信任转发头替代对端 IP。不满足条件时可按既有规则查询，但团队写接口返回不可用。`/status` 返回实际团队写入能力供界面显示。生产启动阻断继续保留。

资金、价格发布、提高预算/并发、密钥轮换等后续流程不因此免审；这些动作仍在对应增量中单独设计和验收。

## 2. 当前事实与方案选择

代码基线：`b11d86a`。已有独立 Admin 身份、HttpOnly 会话、MFA/恢复码、登录限流、Origin 校验、只追加审计及十个只读菜单。

- `permissions.ts` 只包含六个硬编码角色，没有 `super_admin`。
- 角色保存在账号/邀请的字符串数组中；角色页为静态列表，没有在线成员写接口。
- 首页与告警部分依据角色名称决定数据范围，不能仅增加菜单权限就宣称自定义角色可用。
- `weiys01@126.com` 当前为 `system_admin + owner`；`weiys02@126.com` 为 `system_admin`。本批实现后才迁移第一位为真正的超级管理员。
- 两个账号的已有密码和本机免 MFA 例外保持不变；不把短密码或免 MFA 自动扩展给所有新成员。

采用“现有模块内增加成员/角色命令服务＋数据库角色目录”。相比继续追加硬编码按钮，可以正确支持自定义角色；相比引入第三方 IAM 或完整审批引擎，复用现有身份与会话即可覆盖本批需求。

## 3. 角色与授权规则

### 3.1 内置角色

| 角色 | 本批职责 | 团队管理范围 |
| --- | --- | --- |
| `super_admin` 超级管理员 | 拥有本版本全部已实现的非敏感管理权限 | 可管理他人、分配管理角色、管理自定义角色；受自保护规则约束 |
| `system_admin` 系统管理员 | 保留系统/审计查询，增加普通成员管理 | 可邀请、编辑、分配普通角色、启禁用、重置普通成员密码 |
| `owner` 业务负责人 | 保留全部现有业务查询，增加普通成员管理 | 与系统管理员相同，不可管理其他管理人员 |
| `support` / `finance` / `model_operator` / `content_operator` | 保留各自现有查询能力 | 默认无团队写权限 |

管理人员指拥有 `super_admin`、`system_admin`、`owner` 中任一角色的账号或邀请；其余为普通成员。拥有多角色时，只要含管理角色，就按管理人员保护。具有非空 `extraPermissions` 的账号或邀请也作为受保护目标，仅超级管理员可执行本批管理动作，但仍不可修改其敏感额外权限。仅超级管理员可给他人分配/移除管理角色或操作其他管理人员。

系统管理员与业务负责人可以为普通成员选择任意现有普通内置角色或普通自定义角色。这是明确的“普通成员权限委派”能力，不要求所委派的业务读取权限必须是操作者本人拥有的权限。该能力不能用于改变自己的角色、改动受保护目标、创建管理角色或授予敏感内容权限。

`super_admin` 使用显式版本化权限集合，不采用 `*`，不自动获得未来尚未实现的权限。模型凭据、客户原图/提示词、会话令牌等不因超级管理员身份自动变成可读。

### 3.2 权限目录

保留既有读权限，新增以下动作权限：

| 权限 | 行为 | 默认内置角色 |
| --- | --- | --- |
| `admins.create` | 新建邀请、重新生成或撤销邀请 | 三种管理角色 |
| `admins.update` | 编辑显示名称，允许编辑本人名称 | 三种管理角色 |
| `admins.roles.assign` | 更改他人的角色集合 | 三种管理角色，另检查目标/角色级别 |
| `admins.status.update` | 启用或禁用他人 | 三种管理角色 |
| `admins.password.reset` | 为他人生成密码重置链接 | 三种管理角色 |
| `roles.read` | 查看角色、权限及成员数 | 三种管理角色 |
| `roles.create` / `roles.update` / `roles.delete` | 管理自定义角色 | 仅超级管理员 |

权限目录同时记录中文名称、模块、依赖权限、是否可用于自定义角色。动作端点拒绝未知字段及未知权限。所有管理动作均依赖 `admins.read`；角色写动作依赖 `roles.read`。

自定义角色首版仅组合本版本的业务/系统查询权限及其数据范围权限；不得包含团队写权限、角色写权限、敏感读取权限或未来业务写权限。超级管理员是受保护内置角色，不能通过自定义角色复制。

`extraPermissions` 的既有敏感授权机制保持独立；成员/角色表单和写接口不能修改它。后台仍对敏感读取执行独立授权、访问理由和短期授权校验。

### 3.3 数据范围统一

新增显式读取能力：`dashboard.business.read`、`dashboard.finance.read`、`dashboard.models.read`、`dashboard.system.read`、`dashboard.content.read`、`alerts.service.read`、`alerts.model.read`。

这些权限只限定已有指标/告警分类，不新增尚未收集的统计。内置角色的数据范围明确如下；多角色取并集，但仍检查底层资源权限。

| 角色 | 首页范围 | 告警分类 |
| --- | --- | --- |
| super_admin | business、finance、models、system、content | service、model |
| owner | business、finance、models、system | service、model |
| support | business | service |
| finance | business、finance | 无 |
| model_operator | models | model |
| system_admin | system | 无 |
| content_operator | content（仅现有未接入说明） | 无 |

业务总量指标需 `dashboard.business.read + users.read + orders.read + jobs.read`，不因拥有首页权限就暴露全部数量。

所有首页分组还需校验底层资源权限，例如财务概览需要 `orders.read + credits.read`，模型概览需要 `models.read`，系统人数需要 `admins.read`；告警类别需同时具有 `alerts.read` 与对应类别权限。成本字段始终额外检查 `costs.read`。角色编辑器自动补足并展示依赖，后端拒绝依赖不完整的权限集合。

登录、每次请求重授权、菜单、字段投影、首页和告警全部使用同一个权限解析结果；业务查询层不得再通过 `actor.roles.includes('owner')` 等名称特判数据范围。

### 3.4 自保护与锁定规则

- 禁止在团队管理中禁用自己、更改自己的角色或重置自己的密码；可编辑自己的显示名称。界面显示不可用原因，后端同样拒绝。
- 超级管理员之间可以互相管理，但不能移除最后一位可登录超级管理员。通过同一数据库事务内的共享保护锁执行检查，不能采用先 count 后独立 update。
- 可登录指：未禁用且已完成 MFA 的 active 账号；或当前有效本地免 MFA 配置明确涵盖的 pending 账号。单纯持有邀请、未完成 MFA 且不在例外名单中的 pending 账号不计数。
- 给账号授予 `super_admin` 前，该账号须满足上述可登录条件；邀请不能直接绑定 `super_admin`。可先邀请为其他角色，激活后再提升。
- 管理角色不能在线编辑、重命名或删除。自定义角色只有无人使用且无有效未消费邀请引用时才允许删除。
- 账号仅启用/禁用，不做物理删除；邮箱作为登录身份在本批不可编辑，避免静默替换身份或改变本地例外适用范围。

## 4. 团队成员操作流程

### 4.1 新增成员与邀请

“团队成员”提供“成员”“待激活邀请”两个页签和“新增成员”按钮。新增表单：邮箱、显示名称、至少一个可分配角色、操作原因。邮箱规范化为 trim/lowercase；名称 1–80 字符，原因 5–500 字符，角色最多 10 个且去重。

提交后保存 24 小时有效的一次性邀请；**返回可复制邀请链接，不声称已发送邮件**。受邀人打开现有邀请激活页，设置自己的密码并完成适用的登录流程。邀请的显示名称作为激活初值，受邀人可修改自己的显示名称，不能自行改变邀请角色。

邀请链接仅在生成成功的响应中显示一次。列表仅显示邮箱、名称、角色、状态、到期时间，不返回 token；遗失链接可明确执行“重新生成”，使旧链接立刻失效。复制失败保留弹窗，可手动选取，不自动创建新邀请。

同邮箱已有账号时拒绝重复创建并引导查找该成员；有效未消费邀请存在时返回冲突，不能静默更换权限。过期/已撤销且未消费的邀请可在原记录上重新生成，更新版本并留痕。被撤销或过期的 token 不得激活。

待激活邀请可修改显示名称和角色；角色变化时撤销旧链接并要求明确重新生成链接，避免已经分发的邀请静默获得更大权限。已消费邀请只展示历史，不可修改。

新增账号不预置公共默认密码、不发送真实邮件；保持现有对两个指定本地账号的登录例外。新成员默认沿用现有 12 字符密码/MFA 流程，界面在生成邀请前明确提示。

### 4.2 编辑成员与分配角色

详情返回完整工作邮箱、显示名称、账号状态、是否已激活、角色标签、创建时间、版本及 `allowedActions`。仅具备团队读取权限者可查看必要的完整内部工作邮箱；不改变客户邮箱脱敏规则。

编辑表单只能提交显示名称；角色通过独立弹窗提交完整的目标角色集合及操作原因，显示前后差异。角色不得为空、未知、重复或引用已删除角色。变更成功后撤销目标旧会话/挑战并提升 `authVersion`，目标下次登录即应用新权限。

资料编辑增加记录版本但不踢出登录。多管理员同时编辑时，过期版本返回 409，不覆盖他人修改；表单保留输入并提示重新加载比较。

### 4.3 启用与禁用

禁用确认展示邮箱、角色、影响及必填原因。提交后设置禁用标记，对外状态显示 disabled，撤销全部会话、挑战和未消费密码重置链接；保留所有业务关联和审计。任何旧 Cookie 均不可继续访问。

新增 `disabledAt` 表示管理禁用；原有 pending/active 表示激活进度。迁移将既有 disabled 映射为 `disabledAt` 非空，激活进度根据 MFA 完成证据恢复，无法证明已激活则按 pending 处理。对外展示“已禁用”优先于激活状态。

启用只清除 `disabledAt`，不伪造 MFA 已完成；重新登录仍需通过该账号适用的流程。不会恢复旧会话、已撤销的邀请或重置链接。禁止对本人操作，保护最后一位超级管理员。

### 4.4 重置密码

“重置密码”生成绑定账号、30 分钟有效的一次性链接，由操作者复制给本人；管理员不能查看旧密码，也不能从成员列表读到临时密码。

发起重置立即撤销目标已有会话/挑战和旧重置链接，但不修改密码、不修改 MFA、不自动启用禁用账号。禁用账号不允许生成重置链接。受邀但尚未创建账号者使用重新生成邀请，不走密码重置。

重置页要求 token、匹配邮箱及新密码；消费 token 与更新密码、提升 `authVersion`、撤销会话在同一事务中完成。成功后回到登录，不把重置链接当作业务会话；账号仍按原 MFA/本地例外规则登录。错误、失效及已使用链接统一提示，不通过匿名查询枚举账号。

链接不会取消 MFA；不提供 MFA 重置、代登录或读取恢复码。本地两位账号不会被自动重置密码。

## 5. 角色管理界面与行为

角色列表显示名称、标识、内置/自定义、成员数、权限摘要；支持名称/标识查询、查看详情。内置角色仅查看，明确标记受保护。没有角色写权限时保留查看，按钮展示权限不足说明。

“新增角色”填写中文名称、唯一标识、说明、权限勾选和原因。标识使用 `custom_` 前缀及小写字母/数字/下划线，总长不超过 64；名称 1–80 字符，说明不超过 500。至少含 `dashboard.read`，其余从可选权限目录选择。

编辑不能修改标识，可修改名称、说明和可选权限。保存前展示受影响成员数。权限变更在事务内提升所有受影响账号的 `authVersion`、撤销会话与挑战；未消费邀请下次激活读取新权限，同时清晰展示角色权限已变更。仅名称/说明变化不撤销会话。

删除仅支持无账号绑定、无有效邀请引用的自定义角色；被使用时返回冲突及数量，提示先解除引用。删除采用逻辑删除，保留标识唯一性和审计可追溯性，不将历史标识重新用于不同角色。

## 6. 后端结构与数据设计

仍在现有 NestJS admin 模块内实现，不拆服务、不复制业务库：

- `AdminPermissionService`：解析内置/自定义角色、权限依赖、目标保护、数据范围；认证和查询层共用。
- `AdminMembersService/Controller`：成员和邀请命令、列表/详情及可用动作。
- `AdminRolesService/Controller`：权限目录、角色 CRUD 和受影响成员失效处理。
- `AdminPasswordResetService`：一次性重置凭证签发/消费及匿名限流。
- 复用 `AdminAuthService`、Origin/会话守卫、`AdminAuditService`；抽取公共事务锁/撤销会话助手，避免多处规则不一致。

### 数据变更

| 对象 | 变更及约束 |
| --- | --- |
| `AdminRole` | `key` 主键、name、description、builtIn、permissions 字符串数组、version、deletedAt、createdAt、updatedAt；权限只能来自目录 |
| `AdminAccountRole` | accountId / roleKey 联合唯一、外键；账号角色绑定唯一来源 |
| `AdminInvitationRole` | invitationId / roleKey 联合唯一、外键；邀请角色绑定唯一来源 |
| `AdminAccount` | 增加 version、updatedAt、disabledAt；现有 authVersion 继续用于会话失效；迁移后去除旧 roles 数组读写 |
| `AdminInvitation` | 增加 displayName、version、updatedAt、revokedAt、createdBy；已有 expiresAt/consumedAt/tokenHash 复用；迁移后去除旧 roles 数组读写 |
| `AdminPasswordReset` | id、accountId、tokenHash 唯一、expiresAt、consumedAt、revokedAt、createdBy、createdAt；从不保存明文 token |
| `AdminCommandReceipt` | 操作者、会话、幂等键、动作、目标、请求摘要、非敏感结果摘要、完成时间；操作者＋幂等键唯一 |
| `AdminAuditEvent` | 增加受限 metadata JSON：动作对象、变更字段名、前后角色 key/状态/version、关联凭证 ID；继续只追加 |

内置角色由版本化迁移写入，在线服务不允许修改 builtIn 记录；自定义角色只能包含可选查询权限。迁移对旧角色数组逐个校验，未知角色导致迁移失败并报告账号 ID，不丢弃旧角色后默默继续。保留 `extraPermissions`，不把它混入普通角色目录。

迁移在维护窗口执行，停旧后台进程后单事务转换现有账号/邀请绑定及状态；新代码只读关系表，不长期双写。迁移失败完整回滚，重启旧版本；迁移成功后若需代码回退，先根据备份与绑定关系制定反向迁移，不直接启动不能理解新结构的旧代码。

## 7. API 与交互契约

沿用 `/api/admin`、成功响应 `{ data, message, requestId }` 和既有错误信封。既有只读资源接口保持兼容；成员/角色旧列表不静默改成不同 JSON 形状，专用管理页使用新端点。

| 方法与相对路径 | 用途 |
| --- | --- |
| `GET /team/members`、`GET /team/members/:id` | 分页成员及详情/可用动作 |
| `PATCH /team/members/:id` | 更新显示名称 |
| `PUT /team/members/:id/roles` | 替换角色集合 |
| `POST /team/members/:id/enable`、`/disable` | 启禁用 |
| `POST /team/members/:id/password-resets` | 签发一次性密码重置链接 |
| `GET /team/invitations`、`POST /team/invitations` | 邀请查询/新增并返回一次链接 |
| `PATCH /team/invitations/:id` | 修改未消费邀请资料/角色 |
| `POST /team/invitations/:id/rotate`、`/revoke` | 重新生成链接/撤销 |
| `GET /team/roles`、`GET /team/roles/:key` | 专用角色列表/详情 |
| `GET /team/permission-catalog` | 可选权限、依赖和分配边界 |
| `POST /team/roles`、`PATCH /team/roles/:key`、`DELETE /team/roles/:key` | 自定义角色创建/编辑/逻辑删除 |
| `POST /auth/password-resets/accept` | 匿名消费一次性重置链接；有独立限流与 Origin 校验 |

管理写请求均带 `Idempotency-Key`、原因，修改现有对象还带 `expectedVersion`；DELETE 的原因和版本放入 JSON 请求体，不写入 URL。列表每页 30、最多 100，稳定游标；成员支持邮箱精确查询、状态、角色筛选，邀请支持邮箱和有效状态筛选。

邀请创建需 `admins.create + admins.roles.assign`；邀请资料修改、旋转、撤销需 `admins.create`，涉及角色修改时再检查 `admins.roles.assign`。所有邀请动作都执行与成员一致的目标级别/角色分配检查，不因目标尚未激活而绕过保护。

每个对象返回 `allowedActions: [{ action, allowed, reasonCode }]`。客户端决定按钮与说明，但服务端提交时再检查权限、目标、版本及环境。400 表示输入错误，401 会话失效，403 越权，404 不存在，409 版本/引用/自保护/幂等冲突，429 限流，503 团队写功能未在当前环境开放；错误附稳定业务码和中文说明。

幂等键重放返回已提交的非敏感结果，不重复执行。相同键对应不同规范化请求摘要则返回冲突；摘要中不包含密码、token、密钥。邀请/重置链接只在第一次响应返回明文，重放明确返回“已生成但不能再次读取，请重新生成”，不假装可以恢复原链接。数据库不保存明文响应快照；重新生成须新的明确操作和幂等键。

匿名重置消费不使用管理命令凭证；其 token 散列、单次消费及事务保证不可重放。所有链接使用已配置的管理前端 Origin 构造，不信任请求 Host，不接受任意跳转地址；token 放 URL fragment，前端读取后移除，绝不写入查询日志、分析事件或持久化浏览器存储。

## 8. 一致性、并发与审计

本批操作只修改 PostgreSQL，不需要队列或外部执行状态机。每次写操作在一个事务中完成：当前会话重授权 → 环境/动作/目标保护 → 版本和幂等校验 → 修改 → 会话失效 → 审计 → 命令回执。

采用共享的权限目录/团队写保护 advisory lock 串行化低频团队变更；涉及账号、邮箱、邀请的锁继续复用现有规则。所有进入该保护锁的流程必须先取全局保护锁，再按固定顺序取邮箱、邀请、排序账号锁；登录、邀请激活、MFA、重置消费、Bootstrap 和敏感请求等现有认证路径也需统一锁次序，禁止在持有账号锁后反向获取全局锁。

角色权限更新、成员授权、邀请消费与最后一位超级管理员保护必须共享上述串行化边界。事务内二次授权防止页面加载后操作者被禁用/降权仍写入。不持有数据库事务等待网络调用或用户确认。

撤销覆盖目标 session、challenge、短期敏感授权；角色变化/密码变化同时提升 authVersion。仅在幂等命令真正首次执行时追加成功审计。拒绝的越权/自保护动作在独立、最小审计事务留痕，不因业务事务回滚而全部丢失；限流避免日志放大。

审计只记录操作者/会话、对象、字段名、角色 key/状态/version 的必要前后值、原因摘要和结果；不记录密码及散列、邀请/重置 token、MFA 秘钥、完整表单或客户内容。界面在操作前提示原因不得填写密码等秘密；服务器不将完整请求体写入通用日志。

## 9. 前端实现边界

新增独立成员、邀请、角色管理页面和类型化表单，复用现有布局、HTTP 客户端、表格与反馈样式。不把所有 CRUD 塞进通用 `ResourcePage`。

保存中防重复点击；只有收到持久化成功响应才显示成功，随后失效并刷新对应查询。网络断开显示“结果未确认”，同一幂等键查询/重试，不自动创建新的操作。收到 401 清理管理缓存并回到登录；403 重新获取权限后更新按钮；409 保留输入但阻止旧版本覆盖。

表单具备中文字段说明、字段级错误、键盘焦点与关闭确认；角色弹窗显示真实权限摘要而非只显示英文枚举。禁用/重置/角色变更确认框必须标明影响对象。

顶部状态改为实际环境＋“团队管理 B1”；团队/角色页显示已开放动作，其余模块明确只读，不出现“全平台编辑已开放”的误导。无权限、功能未开放、空数据、错误和加载分别展示。

## 11. 验收标准

### 后端与数据库

- 旧角色/邀请完整迁移；自定义角色绑定有外键，未知/已删除角色无法使用；实际登录和每次请求均读取同一角色源。
- 三种管理角色可按范围创建普通成员邀请；普通角色拒绝所有团队写接口；系统管理员不能修改管理人员或授予管理角色。
- 超级管理员可管理其他管理人员及自定义角色；不能自增权/自禁用，不能移除最后一位可登录超级管理员。
- 覆盖同时撤销两位超级管理员、角色编辑与成员绑定并发、邀请修改与激活并发、重置/禁用与旧会话并发，结果符合保护规则且不死锁。
- 邀请24小时、重置30分钟、仅一次消费；旧链接旋转后失效；重复提交不重复写入；已提交响应丢失不会泄露或重复签发原 token。
- 非回环、非 development、伪造 Origin/转发头、过期版本、越权目标、未知字段均拒绝；local_password 例外仍只限现有明确允许账号。
- 角色变更后的首页、告警分类及费用字段与权限一致；自定义角色没有因名称陌生而丢失范围，也不会凭一个首页权限获得全部数据。
- 成功修改与审计原子提交，失败不产生部分状态；日志/响应/回执无密码、密钥和不必要敏感数据。

### 前端与端到端

- 成员/邀请/角色表单可创建、编辑、验证、取消和刷新；成功结果真实读回。
- 各角色按钮可见性/不可用原因正确，直接调用越权接口仍失败。
- 409 保留输入，401 清缓存，503 提示功能未开放；丢响应重试同幂等键不重复执行。
- 本地现有两个账号原登录路径不回退到12字符/MFA拦截；非例外账号继续遵循原安全策略。
- 新成员从邀请到设密/激活/登录形成闭环；密码重置不绕过 MFA 或自动启用账号。
- 全部原后端测试、前端测试、类型检查、Lint、构建通过；新增功能先有失败测试再实现，数据库测试使用隔离数据。

交付时明确列出本批实际可写菜单、仍只读菜单和验证结果，不以“超级管理员已存在”代表后续所有模块已经开发完成。
