# Payments Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement disabled-by-default WeChat Native and Alipay page payments with durable, idempotent paid-credit fulfillment.
**Architecture:** Isolated payment adapters normalize verified facts. Billing service serializes wallet mutations and persists orders before external calls. Dedicated billing UI never uses mock fulfillment.
**Tech Stack:** Existing NestJS, Prisma/PostgreSQL, React, TypeScript, Node 22; official alipay-sdk and local QR rendering.
**Spec:** `docs/superpowers/specs/2026-09-07-payments-design.md`

## Global Constraints

- No live charges, refunds, deployment or credentials in chat/logs; default disabled.
- Preserve existing frontend changes. Work only in the linked `codex/viviai-frontend` worktree.
- Prices are integer CNY minor units, server-controlled; no automatic renewal or unimplemented concurrency entitlements.
- Paid facts must match immutable order and merchant identity; wallet lock before order updates; no network in SQL transactions.
- Unit tests use real generated RSA/AES fixtures; PostgreSQL integration tests use owned isolated schemas.

### Task 1: Official protocol adapters

Files: create `viviai-server/src/modules/billing/{contracts,wechat,alipay,payment-security}.ts`, `viviai-server/test/payment-adapters.test.ts`; update server package lock for official alipay-sdk only.

Interfaces (define in contracts.ts):
```ts
type PaymentChannel = 'wechat' | 'alipay';
type Checkout = { kind: 'qr' | 'redirect'; url: string };
type PaymentRequest = { orderNo: string; amountMinor: number; description: string; expiresAt: Date };
type PaidFact = { channel: PaymentChannel; eventId: string; orderNo: string; tradeNo: string; merchantId: string; appId: string; amountMinor: number; currency: 'CNY'; paidAt: Date };
interface PaymentAdapter {
  readonly channel: PaymentChannel;
  readonly merchantId: string;
  readonly appId: string;
  create(input: PaymentRequest): Promise<Checkout>;
  query(orderNo: string): Promise<PaidFact | null>;
  verifyNotification(rawBody: Buffer, headers: Record<string, string | string[] | undefined>): PaidFact | null;
}
```

- [ ] Write adapter tests first: valid signed/encrypted WeChat success yields 2900 fen; changing byte/signature/merchant/app/time/key ID rejects; signed responses verified before interpreting checkout/query; Alipay decoded form RSA2 signature, duplicate fields reject, decimal `29.01` yields 2901, wrong seller/app/amount/state reject; valid page URL only official domain. HTTP transport may be injected at its external boundary, no test scenario in public API.
- [ ] Run `npx vitest run test/payment-adapters.test.ts` and record missing-feature failure.
- [ ] Implement adapters with strict lengths/required fields, finite dates, fixed official hosts, 10s timeout, bounded response payload, no redirect-follow. Export constructors accepting explicit config objects; no env reads in adapters. Return null only authenticated unpaid status. Alipay use official SDK pageExecute/exec(validateSign:true) or documented curl with verified response, checkNotifySignV2.
- [ ] Run focused tests and typecheck; report exact files/contracts, results and red/green evidence.

- [ ] Implement schema with unique user/idempotency key, merchant order number, channel/merchant/trade number and channel/event ID. Financial DB constraints positive finite integers; source order linkage through lot `sourceId=payment:<uuid>`.
- [ ] Implement transactional create claim, immutable snapshots and checkout CAS so early callbacks cannot be undone. On uncertain create, preserve creating state and query before any further create.
